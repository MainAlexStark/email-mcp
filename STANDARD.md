# Стандарт MCP-сервера

Этот документ описывает устройство, общее для `ozon-seller-mcp`,
`k8s-mcp` и `email-mcp`. Он нужен для одной вещи: разобравшись в одном сервере,
не разбираться заново в другом — и подняв третий, не придумывать
всё сначала.

Правила здесь не про красоту. Каждое стоит за конкретной поломкой,
и она названа рядом.

## 1. Структура репозитория

```
<имя-сервера>/
├── .github/workflows/ci.yml   gofmt + vet + build + test -race
├── .gitignore                 bin/, .env, деплойный env-файл
├── Dockerfile                 многослойная сборка → distroless nonroot
├── LICENSE
├── Makefile                   build, install, test, fmt, check, verify
├── README.md                  как поставить, как подключить, что умеет
├── STANDARD.md                этот файл
├── deploy.sh                  развернуть и обновить на VPS одной командой
├── docker-compose.yaml        сервер за общим Caddy
├── go.mod                     module github.com/<owner>/<имя-сервера>
│
├── cmd/<имя-сервера>/         имя каталога = имя бинарника
│   ├── main.go                флаги, окружение, сборка сервера, транспорт
│   ├── admin.go               --hash-password, --grants, --revoke
│   └── errors.go              локальные обёртки, чтобы main.go читался
│
├── deploy/
│   ├── <имя>.env.example      все переменные с объяснениями
│   ├── <имя>.env              секреты; пишет deploy.sh, в git не попадает
│   └── <имя>.service          systemd-юнит с ограничениями прав
│
├── docs/
│   ├── OAUTH.md               подключение устройств
│   ├── REMOTE.md              сетевой режим
│   ├── TOOLS.md               полный список инструментов
│   └── <DOMAIN>.md            то, что специфично: NETWORK.md, DEPLOY.md
│
├── internal/
│   ├── httpx/                 сетевой транспорт и авторизация
│   ├── mcp/                   тонкий слой над официальным Go SDK
│   ├── mcptest/               клиент MCP для тестов
│   ├── oauth/                 OAuth 2.1: свой authorization server
│   └── tools/                 инструменты, схемы, защита
│
└── <домен>/                   клиент внешней системы: ozon/, kube/
```

Каталог домена (`ozon/`, `kube/`) лежит в корне, а не в `internal/`,
намеренно: это самостоятельная библиотека, которую можно взять отдельно
от MCP. Плоская структура внутри — один файл на тему, без подпакетов.

## 2. Три слоя и их границы

| Слой | Знает про | Не знает про |
|---|---|---|
| `<домен>/` | внешнюю систему | MCP, JSON-RPC, инструменты |
| `internal/mcp` | протокол и SDK | предметную область |
| `internal/tools` | оба | транспорт и авторизацию |
| `internal/httpx` | HTTP, токены, права | устройство инструментов |

Граница между `internal/mcp` и `internal/tools` — главная. Она означает,
что смена версии протокола (а он меняется несколько раз в год)
останавливается в одном файле и не расходится по тридцати инструментам.

`internal/mcp` держит ровно два типа — `Tool` и `Server` — и два способа
отдать набор инструментов: `Serve` (stdio) и `StreamableHandler` (HTTP).
Инструменты регистрируются низкоуровневым `AddTool`: аргументы доходят
сырым `json.RawMessage`, схема задаётся картой. Типизированный
`mcp.AddTool` из SDK проверял бы аргументы сам, но тогда описание
инструмента растекается по структуре Go, тегам и отдельному файлу на
каждый вызов, а проверки прав и обрезка ответа проходят мимо.

Ресурсы MCP (если они есть) объявляются отдельным файлом
`internal/mcp/resource.go`, чтобы `server.go` оставался общим для всех
серверов и сверялся построчно.

## 3. Реестр инструментов

Один `Registry` на весь сервер: клиент домена, `Safety`, `*mcp.Server`.
Инструменты описываются спецификацией и регистрируются группами по
доменным темам — `RegisterPods()`, `RegisterPricing()` — по файлу на
тему в `internal/tools`.

```go
r.Add(Spec{
    Name:   "list_pods",
    Desc:   "Что делает и когда пригодится.",
    Write:  false,
    Schema: schema(obj{"namespace": namespaceField()}),
    Do:     func(ctx context.Context, a Args) (any, error) { … },
})
```

В `Registry.Add` — и только там — стоят:

1. разбор аргументов и ошибка «не разобрать аргументы»;
2. `Safety.CheckWrite` для `Write: true`;
3. доменные подтверждения (размер пачки, защищённый namespace);
4. вызов;
5. подсказка к отказу;
6. сериализация и обрезка ответа.

Причина ровно одна: пропустить проверку в одном из восьми пишущих
инструментов — вопрос времени, а цена забывчивости — удалённый под
в `kube-system` или цена 690 вместо 6900.

Для того, что не укладывается в `Spec`, есть `AddCustom(mcp.Tool)` —
им пользуются диагностические инструменты.

Схемы пишутся сокращениями из `internal/tools/errors.go`: `obj`,
`schema`, `str`, `num`, `boolean`, `arr`. Схема — это то, что видит
модель; поле без описания она заполняет догадкой, поэтому экономить
надо на скобках, а не на словах.

## 4. Безопасность: заслоны, а не просьбы

Системный промпт — не архитектурная граница. Всё, что нельзя разрешать
формулировкой в чате, закрывается кодом.

**Режим по умолчанию — только чтение.** `Safety.Mode` — `read-only`,
пока человек не открыл запись переменной окружения (stdio) или пишущим
токеном (сеть). Текст отказа обязан называть оба случая: инструмент
один и тот же, а чинить надо разное.

**Права — свойство запроса, а не процесса.** `Safety` кладётся в
контекст запроса в `internal/httpx` после проверки токена, инструменты
читают её оттуда (`SafetyFrom`). Настройки процесса остаются запасным
значением для stdio. `SafetyFrom` возвращает второе значение «были ли
права заданы»: молча подставить разрешающие настройки, когда в контексте
пусто, — ровно тот способ, которым такие проверки и обходят.

**Доменная страховка от дорогой опечатки.** У каждого сервера своя:
у Ozon — порог изменения цены (6900 → 690 проходит любую проверку
формата и молча уничтожает маржу), у Kubernetes — подтверждение для
системных namespace. Обходится явным аргументом (`confirm_large_change`,
`confirm`), который модель обязана выставить после согласия человека.

**Потолок размера ответа.** Клиент режет результат инструмента по числу
токенов; ответ сверх этого не доезжает вовсе, модель видит отказ и
повторяет вызов. Поэтому длинный JSON обрезается по элементам самого
объёмного массива — наружу выходит валидный документ с отметкой
`_trimmed`, числом оставшихся элементов и подсказкой, как сузить
выборку. Не-JSON режется по байтам с проверкой на корректный UTF-8:
битая кодировка ломает уже не смысл ответа, а протокол.

## 5. Два транспорта, одна реализация

- **stdio** — клиент запускает сервер подпроцессом. Диагностика уходит
  в stderr: stdout занят протоколом.
- **Streamable HTTP** — `--http` или `<PREFIX>_HTTP_ADDR`. Без состояния:
  ни `Mcp-Session-Id`, ни его требования. Поэтому сервер переживает
  перезапуск и не ломается за балансировщиком.

`JSONResponse: true` — сервер ничего не шлёт по своей инициативе,
а с обычным JSON проще жить автоматизации со статическим токеном.

`DisableLocalhostProtection: true` — встроенная в SDK защита от DNS
rebinding отклоняет запрос, пришедший на локальный адрес с внешним
`Host`, а это ровно штатная схема развёртывания за обратным прокси.
Проверка `Origin` сделана отдельно в `internal/httpx` и работает для
всех запросов.

**Сетевой сервер не стартует без авторизации** (`httpx.ErrNoAuth`).
Не опция, а условие запуска.

## 6. Авторизация

OAuth 2.1 — основной способ для людей: сервер играет обе роли сразу,
пользователь один (владелец), «вход» — проверка одного пароля.
Динамическая регистрация клиентов, PKCE, экран согласия с галочками
прав, токен на час, refresh, поштучный отзыв (`--grants`, `--revoke`).

Статические токены (`<PREFIX>_TOKEN_READ`, `<PREFIX>_TOKEN_WRITE`) —
только для автоматизации, которая не может пройти экран согласия.
Сервер предупреждает при старте, что они не истекают.

Токена в адресе (`/mcp/<секрет>`) нет и не должно быть: спецификация MCP
это запрещает, а адрес с секретом оседает в журналах прокси и истории
браузера.

Хранилище OAuth переживает перезапуск. Без этого каждый рестарт
отключает все устройства разом.

## 7. Переменные окружения

Общий префикс на сервер: `OZON_`, `K8S_`. Обязательный набор:

| Переменная | Что делает |
|---|---|
| `<P>_ALLOW_WRITES` | stdio: разрешить запись |
| `<P>_HTTP_ADDR` | сеть: адрес прослушивания |
| `<P>_PUBLIC_URL` | сеть: внешний адрес; его наличие включает OAuth |
| `<P>_OWNER_PASSWORD` | сеть: пароль владельца; хеш сервер считает сам |
| `<P>_OWNER_PASSWORD_HASH` | сеть: готовый хеш, когда открытый пароль нежелателен |
| `<P>_OAUTH_STORE` | сеть: файл клиентов и токенов |
| `<P>_RESOURCE_URL` | сеть: адрес MCP, если отличается |
| `<P>_TOKEN_READ` / `<P>_TOKEN_WRITE` | статические токены |
| `<P>_ALLOWED_ORIGINS` | сеть: разрешённые `Origin` |
| `<P>_MAX_RESPONSE_BYTES` | потолок размера ответа |

Плюс доменные пороги. Все они перечислены в шапке `cmd/*/main.go`
и в `deploy/*.env.example` — в двух местах, потому что первое читает
тот, кто правит код, а второе тот, кто разворачивает.

## 8. Флаги команды

| Флаг | Что делает |
|---|---|
| `--http <addr>` | сетевой режим |
| `--check` | проверить доступ к внешней системе и выйти |
| `--gen-token` | выпустить статический токен |
| `--hash-password` | посчитать хеш пароля владельца (читает stdin, не аргумент) |
| `--grants` | показать действующие подключения |
| `--revoke <id>` | отозвать подключение |
| `--version` | версия (подставляется `-ldflags "-X main.version=…"`) |

`--check` существует затем, чтобы не отлаживать молчащий MCP внутри
клиента: он отвечает на вопрос «примут ли меня вообще» до того, как
сервер пропишут в конфигурацию.

## 9. Диагностические инструменты

Два на каждый сервер:

- `<префикс>_status` — режим подключения, пороги защиты, число
  инструментов. Первое, что стоит вызвать, когда непонятно, почему
  инструмент отказывается что-то менять.
- `<префикс>_selftest` — по одному минимальному read-запросу к каждому
  методу или виду ресурса, параллельно, с таймаутом. Отвечает на
  следующий вопрос: а разрешает ли это внешняя система. Если не ответил
  никто — говорит об этом прямо, вместо разбора по одному.

## 10. Тесты

| Файл | Что проверяет |
|---|---|
| `internal/mcp/server_test.go` | протокол: рукопожатие, схема, `isError`, дубликаты |
| `internal/tools/registry_test.go` | сквозной путь: вызов → защита → клиент |
| `internal/tools/safety_test.go` | заслоны поодиночке |
| `internal/tools/trim_test.go` | обрезка оставляет валидный JSON и UTF-8 |
| `internal/httpx/server_test.go` | права из токена доезжают до инструмента |
| `internal/oauth/*_test.go` | поток целиком: регистрация → согласие → токен → отзыв |

Два правила:

**Инструменты вызываются через настоящий протокол** — клиентом из
`internal/mcptest`, с рукопожатием и `tools/call`. Дёргать обработчик
напрямую проще, но тогда из-под теста выпадает ровно тот слой, где
обычно и живут ошибки: форма аргументов и форма ответа.

**Тест проверяет не только что сработало, но и что НЕ сработало.**
Главный вопрос к защите — дошёл ли запрос до внешней системы вопреки
отказу. Поэтому подставной клиент записывает вызовы, а тест смотрит,
что записи там нет.

## 11. Тон кода и документации

Комментарии объясняют «почему», а не «что»: код и так виден. Хороший
комментарий называет поломку, из-за которой строка написана именно так.

Описания инструментов пишутся для модели и говорят, когда инструмент
пригодится, а не только что он делает. Тексты ошибок пишутся для
человека и называют, что именно править и где.

## 12. Развёртывание

Развернуть сервер — одна команда, обновить — одна команда. Это не
удобство: путь, состоящий из восьми шагов, выполняется по памяти
и на третьем развёртывании расходится с документацией.

```bash
./deploy.sh mcp.example.com     развернуть или перенастроить на домен
./deploy.sh update              обновить до свежего коммита
./deploy.sh status | logs | secrets | restart | down
```

`deploy.sh` одинаков во всех серверах стандарта; различаются только
шапка (`APP`, `PREFIX`, `PORT`) и функция `prepare_extra` — то, без чего
именно этот сервер не поднимется: ключи Ozon, kubeconfig.

Что он делает при развёртывании:

1. заводит сеть `mcp-network`;
2. поднимает общий Caddy в `/opt/infrastructure`, если его там нет;
3. вписывает свой блок в общий `Caddyfile` между маркерами
   `# >>> <имя>` и `# <<< <имя>`;
4. придумывает пароль владельца и статические токены, кладёт
   в `deploy/<имя>.env` с правами 600;
5. собирает образ (версия — из `git describe`, попадает в бинарник
   через `-ldflags`) и поднимает сервер;
6. ждёт `200` от `https://<домен>/healthz`.

Четыре решения, которые стоит сохранять при переносе на новый сервер:

**Caddy общий на машину, а не свой у каждого сервера.** Порты 80 и 443
одни, а MCP-серверов на VPS обычно несколько. Каждый вписывает свой блок
и ходит к прокси по имени контейнера внутри `mcp-network`.

**Блок в Caddyfile правится по маркерам, а не поиском по домену.**
Домен может смениться; без маркеров в файле остались бы два блока,
из которых работал бы первый — и чинить это пришлось бы ночью.

**Повторный запуск ничего не перевыпускает.** Пароль и токены
генерируются только если их ещё нет: перевыпуск отключил бы уже
подключённые устройства.

**Обновление откатывается само.** `git pull` → пересборка → ожидание
`/healthz`; если новая версия не ответила за полторы минуты, скрипт
возвращает прежний коммит и поднимает его. Без отката неудачное
обновление оставляет сервер лежать до ручного разбора, и узнаёте вы
об этом от того, кто им пользуется.

Отсюда же требование к серверу: **пароль владельца задаётся открытым
текстом** (`<P>_OWNER_PASSWORD`), а PBKDF2-хеш сервер считает сам при
старте. Отдельный шаг «сгенерируйте хеш и вставьте строку» нельзя
выполнить одной командой, и именно на нём застревает развёртывание.
`--hash-password` остаётся для тех, кому открытый пароль в окружении
нежелателен даже в файле с правами 600; заданный хеш имеет приоритет.

## 13. Чек-лист нового сервера

1. `go mod init github.com/<owner>/<имя>`, каталоги по разделу 1.
2. Скопировать `internal/mcp`, `internal/mcptest`, `internal/httpx`,
   `internal/oauth` — они не зависят от предметной области, меняются
   только тексты и префикс переменных.
3. Написать `<домен>/`: клиент, типы ответов, `Hint(err)` с разбором
   классов отказа.
4. `internal/tools`: `safety.go` (режим + доменная страховка),
   `context.go`, `registry.go`, `errors.go` (сокращения схем),
   `trim.go`, `defaults.go` (разбор аргументов), файл на доменную тему.
5. `diagnostics.go`: `status` и `selftest`.
6. `cmd/<имя>/`: флаги из раздела 8, переменные из раздела 7.
7. Тесты из раздела 10 — начиная с «запись запрещена по умолчанию».
8. `Makefile`, `.github/workflows/ci.yml`, `Dockerfile`,
   `docker-compose.yaml`, `deploy/`, `README.md`, `docs/`.
9. `deploy.sh`: скопировать из соседнего сервера, поменять шапку
   (`APP`, `PREFIX`, `PORT`, `APP_DNS_HINT`, `USAGE_EXTRA`) и написать
   `prepare_extra` — остальное общее и правке не подлежит.

## Отступление: ozon-seller-mcp как сервис

С переходом на многопользовательский режим ozon-seller-mcp отошёл от стандарта в сетевой части — сознательно, потому что однопользовательская схема стандарта (пароль владельца, ключи в окружении, `oauth.json`) для сервиса не подходит:

- состояние в PostgreSQL (`internal/pgstore`), а не в файле; хранилище OAuth — интерфейс `oauth.Storage`;
- вместо пароля владельца — учётные записи и веб-кабинет (`internal/web`); OAuth спрашивает у кабинета, кто вошёл и какие у него магазины (`oauth.Accounts`);
- вместо `<P>_TOKEN_READ/WRITE` — персональные API-токены из кабинета;
- клиент внешнего API — свойство запроса, а не процесса (`tools.WithClient`);
- `deploy.sh` поднимает базу и мастер-ключ шифрования, есть `backup` и `users`.

stdio-режим, инструменты, заслоны записи и структура `internal/tools` остались по стандарту. Для однопользовательского сервера (k8s-mcp) стандарт в прежнем виде по-прежнему правильный.

## Отступление: email-mcp

Сервисная часть — как у ozon-seller-mcp (PostgreSQL, кабинет, `oauth.Accounts`, персональные токены, `deploy.sh` с базой и мастер-ключом). Отличия, продиктованные почтой:

- **Подключение — ко всем ящикам пользователя или к одному.** Ящик выбирается аргументом `account_id`: переписка у людей идёт из нескольких ящиков сразу. `Subject.MailboxID == 0` — все ящики, включая добавленные позже.
- **Четыре права вместо двух:** `mail:read`, `mail:drafts`, `mail:write`, `mail:send`. Вместо `Safety.Mode` — флаги `Drafts/Write/Send`, вместо `Spec.Write` — `Spec.Access`. Доменная страховка — `confirm` на удаление и порог получателей с `confirm_many_recipients`.
- **Регистрация в трёх режимах:** `MAIL_REGISTRATION=open|invite|closed`; приглашения — `--invite N`, `./deploy.sh invite`.
- **Адреса внешней системы вводит пользователь,** поэтому клиент домена запрещает внутренние адреса и открытый текст (`mail.WithPublicOnly`), если не задан `MAIL_ALLOW_PRIVATE_HOSTS`.
- **Тесты ходят в настоящий IMAP и SMTP** в памяти (`mail/mailtest` на go-imap `imapmemserver` и go-smtp) — подставной HTTP-сервер здесь не годится.
